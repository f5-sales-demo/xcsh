Use `xcsh blindfold` to encrypt private keys with your tenant's public key before creating a certificate resource. RSA and EC keys, encrypted PEM, and single-key PKCS#12 bundles are parsed inside the native module. The installed command requires neither vesctl nor an OpenSSL executable.

[Choose the context and namespace](/xcsh/en/f5-distributed-cloud/contexts-namespaces/) first. Commands use the existing xcsh context and environment rules; certificate namespace
defaults to `XCSH_NAMESPACE`, and secret policy defaults to `shared/ves-io-allow-volterra`. The policy and public key must identify the same canonical tenant.

## Replace the vesctl secrets procedure

Use [immutable xcsh v23.0.0](https://github.com/f5-sales-demo/xcsh/releases/tag/v23.0.0) or later for this interchangeability contract. Earlier v22.15.0 compatibility output has different defaults.

After native [context setup](/xcsh/en/f5-distributed-cloud/contexts-namespaces/), replace only `vesctl` with `xcsh` in the [frozen BYOC
article](https://github.com/A-Haines/xc-lb-byoc-demo-automation/blob/e7acf7fd53b2f19d9aca7ca43f23e47c2187ab9e/examples/blindfold/README.md). Keep this work in a private directory
and set an owner-only umask before shell redirection:

```bash
umask 077
mkdir -p certs
xcsh request secrets get-public-key > pubkey
xcsh request secrets get-policy-document --namespace shared --name ves-io-allow-volterra > policy
xcsh request secrets encrypt --policy-document policy --public-key pubkey key.pem | tail -1 > certs/key.blindfold
```

`certs/key.blindfold` contains one bare-base64 line. The reference consumer trims the file and adds exactly one `string:///` prefix. Its README incorrectly describes the file as a
location string. For existing `xcsh create` commands, set `spec.private_key.blindfold_secret_info.location` to `string:///` followed by that trimmed value. Encryption does not
create a certificate or load balancer.

Released Ubuntu standalone and independent Mac Homebrew v23.0.0 acceptance ran this pipeline, created and rotated fresh certificates on fixed-response HTTPS load balancers, and verified strict private CA trust, SNI, changed fingerprints, ready/valid state and HTTPS 200. All run-owned resources were removed and named absence verified.

The article deploys through the deprecated `volterra` Terraform provider. The next-generation [terraform-provider-xcsh](https://github.com/f5-sales-demo/terraform-provider-xcsh) is
unreleased and still iterating toward feature completeness. Richer Blindfold provider functionality is future work. This guide qualifies xcsh encryption and xcsh-owned resource
deployment; it does not qualify that provider or reproduce the article's deployment stack.

Compatibility public documents default to camelCase YAML. `--outfmt json|yaml` or modern retrieval-only `--output json|yaml` selects an explicit format; do not combine them. Policy
retrieval requires `--name` and defaults its namespace to `default`; the explicit shared policy above is appropriate for platform TLS. Canonical `xcsh blindfold public-key` and
`policy` retain snake_case JSON defaults, and canonical policy defaults to `shared/ves-io-allow-volterra`.

Both command paths use the [native offline document contract](#offline-encryption).
Compatibility encryption defaults to bare base64. Canonical `blindfold encrypt` defaults to `string:///…`. On either path, `--encoding base64|location` chooses explicitly, and `--output-file` stores that selected text atomically in a new mode-0600 file. Compatibility encryption accepts `--outfmt` without changing ciphertext encoding.

```bash
xcsh request secrets encrypt --public-key pubkey --policy-document policy key.pem --encoding location --output-file key.location
xcsh request secrets encrypt --public-key pubkey --policy-document policy key.pem --outfile key.envelope --result-file encrypted.json
```

Compatibility `--outfile` stores the raw binary envelope, with empty default stdout. It conflicts with explicit textual encoding, `--output-file` and `--json`; a distinct
`--result-file` is allowed. Existing or symlink destinations are rejected. The raw artifact is not a location string; use textual output for a location consumer. `--json` and
assistant results remain public reports without ciphertext.

Encryption accepts one positional filename, `--input FILE`, `-` for redirected stdin, or redirected stdin with no filename. Use `--` before filenames beginning with a dash.
Interactive missing input fails immediately. Native bounded, zeroizing reads preserve binary plaintext and support cancellation; Ctrl-C exits 130, usage errors exit 2, and
operational failures exit 1. Diagnostics go to stderr.

Canonical `--policy namespace/name` and modern `-n` remain available. Do not combine canonical policy with explicit policy namespace/name. `--context-name` asserts the selected
online context without activating another context. Compatibility covers only these three secrets commands: native authentication remains required, and `.vesconfig`, VES
credentials, legacy authentication, request abbreviations and output-directory routing remain unsupported.

## Retrieve public encryption material

```bash
xcsh blindfold public-key --output-file tenant-public-key.json
xcsh blindfold policy --policy shared/ves-io-allow-volterra --output-file policy.json
```

These operations authenticate to the selected tenant. Output files must be new; the command publishes them atomically with owner-only permissions. Tenant public material can contain tenant identity, so keep it in your runtime directory.

## Encrypt a secret or prepare a certificate manifest

```bash
xcsh blindfold encrypt --input secret.txt --output-file secret.blindfold
xcsh blindfold certificate --cert chain.pem --key server-key.pem \
  --name example-tls --output-file certificate.json --result-file prepared.json
```

`chain.pem` must list the leaf certificate first, then its issuers. The native parser verifies key correspondence, chain signatures and order, validity dates, supported algorithms,
and encoded size. Supported keys are RSA 2048–8192 bits and EC P-256/P-384. Encoded secret locations and certificate chains are limited to 131072 bytes each.

The manifest encodes the public chain in `spec.certificate_url` and places the encrypted key in `spec.private_key.blindfold_secret_info.location`. It never emits a clear-key
alternative. Raw encryption and manifest preparation print their artifact when no output file or `--json` is selected; use an output file to keep encrypted payloads out of
transcripts.

## Offline encryption

Native commands accept single-document JSON/YAML with known camelCase or snake_case fields. Agreeing aliases are accepted; conflicting aliases, duplicate keys, multiple documents,
malformed fields and mismatched tenants fail. Retrieval preserves complete public policy information; encryption uses only required normalized fields. The public-key and policy
file flags must be supplied together. With both files, encryption runs offline without context resolution, credentials or network access.

```bash
xcsh blindfold public-key --key-version 7 --output-file pubkey.json
xcsh blindfold policy --policy shared/ves-io-allow-volterra --output-file policy.yaml --output yaml
xcsh blindfold encrypt --input secret.txt --public-key pubkey.json \
  --policy-document policy.yaml --output-file secret.location
```

Replace version `7` with an available tenant key version. `--key-version` accepts an unsigned 32-bit integer. Zero selects the server default; a positive request must return that exact version, with no fallback.

For offline certificate preparation, supply the same public documents with the certificate inputs:

```bash
xcsh blindfold certificate --cert chain.pem --key server-key.pem \
  --public-key pubkey.json --policy-document policy.yaml \
  --name example-tls --output-file certificate.json
```

Canonical encrypted output uses `string:///`. Output artifacts require new destinations and are stored atomically with mode-0600 permissions. Keep public tenant documents and encrypted payloads in a private runtime directory. The assistant accepts file paths only; it does not read private inputs into model context.

## Use protected PEM and PKCS#12 inputs

Set a passphrase variable through your shell's protected input or secret manager. Supply only its name:

```bash
xcsh blindfold certificate --cert chain.pem --key protected-key.pem \
  --passphrase-env TLS_INPUT_PASSWORD --name example-tls --output-file protected.json
xcsh blindfold certificate --bundle server.p12 --passphrase-env TLS_INPUT_PASSWORD \
  --name example-tls --output-file bundle.json
```

Do not put literal passwords on the command line. Choose either a bundle or separate certificate/key files. Bundles containing more than one private key fail before deployment, even when aliases collide.

## Create and rotate a certificate

```bash
xcsh blindfold create --cert chain.pem --key server-key.pem --name example-tls \
  --dry-run=client --json --result-file preview.json
xcsh blindfold create --cert chain.pem --key server-key.pem --name example-tls \
  --json --result-file created.json
xcsh blindfold replace --cert rotated-chain.pem --key rotated-key.pem --name example-tls \
  --json --result-file rotated.json
```

Use different report paths for each run. Client dry runs retrieve public material and inspect the target but perform no tenant writes. Creation fails on an existing name; replacement fails when absent. Replacement preserves the writable metadata and certificate options returned by F5's replace form.

F5 rejects a public-key algorithm change while another object uses the certificate. Rotate RSA to RSA or EC to EC. To change algorithms, create another certificate and change the
load balancer's certificate reference. A rejected algorithm change left the previously served RSA certificate working during live acceptance.

## Verify HTTPS after API acceptance

An `accepted` report means named readback matched the submitted certificate and encrypted key. Its readiness is `unverified`: load-balancer propagation and TLS must be checked separately.

For a load balancer referencing the certificate, connect to its allocated VIP with the certificate's intended SNI. Trust your issuing CA and compare the served fingerprint with the public report:

```bash
curl --cacert ca.pem --resolve example.test:443:192.0.2.10 https://example.test/
```

Replace the example hostname and address with your owned load balancer's values. Live source acceptance used a private test CA and a fixed-response route: RSA creation, rotation to
a second RSA pair, and a separate EC certificate each returned HTTP 200 over TLS 1.3 with the expected served SHA-256 fingerprint. The final RSA demo was restored and verified
after EC acceptance.

## Resolve failures and uncertain writes

A wrong password, mismatched key, malformed certificate, expired chain, denied policy, or oversized payload fails before deployment. If a request outcome is uncertain, the service
reads the named resource once before reporting success or an unresolved outcome; it does not automatically retry a mutation. Inspect the named resource and its current fingerprint
before retrying.

Artifacts require a new destination in an existing writable directory. A cancelled operation stops subsequent work; cancellation after a write can require a named read to determine
its outcome. The `xcsh_blindfold` assistant tool accepts file paths and a passphrase environment-variable name, and returns public status, target, fingerprint, and artifact paths.
It keeps private keys, passwords, tokens, and encrypted payloads out of tool results. Session file-access controls apply to each input and output. Plan Mode blocks deployments and
artifact writing.

## Tear down an owned demo

Remove the load balancer first, then the certificate it references:

```bash
xcsh delete http_loadbalancer example-tls-demo -n example-ns
xcsh delete certificate example-tls -n example-ns
```

Verify both named resources are absent. Remove your local private keys, bundles, passphrase variables, and runtime artifacts according to your team's retention policy. Keep ownership and expiry records private for any demo you intentionally retain.

## Native task discovery

Progressive sessions keep optional schemas deferred. Ask about custom certificates, bringing your own certificate (BYOC), protected PEM, PKCS#12, or encrypting a private key. The assistant identifies the native capability and can discover `xcsh_blindfold` with `search_tool_bm25` using `query: "xcsh_blindfold"` and `limit: 1`. The hint itself performs no operation.

Read `xcsh://blindfold/` for the task index, `xcsh://blindfold/encrypt` for public material and offline encryption, `xcsh://blindfold/certificate` for certificate preparation and rotation, and `xcsh://blindfold/verify` for readiness and failure handling. These read-only routes use the native sections of this guide. Resource configuration continues through the existing API and Terraform guidance.
