System prompts are executable product policy. Edit the smallest owned prompt fragment and verify the composed result; do not paste a second copy of guidance already supplied by a capability or plugin.

## What does the eight-point checklist require?

State role and scope, concrete objectives, available tools, tool-use rules, constraints, output contract, uncertainty behavior, and completion criteria. Use direct instructions with observable conditions. Keep provider-specific details out of shared prompts unless the adapter cannot represent them elsewhere.

## How is the system prompt composed?

The runtime builds the system prompt from the core fragment plus active capabilities, workspace guidance, plan state, memory, and extension contributions. Ordering and deduplication tests protect mandatory boundaries. An absent optional plugin must not remove core safety or file-operation instructions.

## How do I audit a prompt change?

Inspect the final composed prompt for representative capability sets, then run the template, application programming interface (API) spec, deduplication, deprecation, workspace-boundary, start-folder, and absent-plugin tests.

Record why each new sentence belongs at that layer, and remove a stale alias rather than documenting both paths.

Read `packages/coding-agent/src/prompts` for the composed fragments and their ordering tests.

Treat the composed prompt, not an individual fragment, as the review artifact. Compare
representative runs with and without the capability that contributes the fragment, and verify that
required instructions occur once and in the intended order. Prompt text can change model behavior
without changing TypeScript types, so a passing build is insufficient; retain a focused composition
assertion and an end-to-end behavior test for the policy being changed.

## How should API examples differ from execution?

Prefer `xcsh_api` for F5 Distributed Cloud API execution. Requested curl examples belong in explanations, documentation, and scripts. Generating an example does not authorize execution: example-only requests must not perform resource discovery, creation, updates, or deletion. An explicit request to execute curl uses the existing shell tool and context, credential, approval, and execution controls, after verifying the effective target.

Ground examples in embedded catalog methods and paths and API-spec payload schemas. Use quoted `"$XCSH_API_URL/api/..."` and `"Authorization: APIToken $XCSH_API_TOKEN"`; explain the API base URL and token variables without displaying their values. Match the documented method, substituted path parameters, Content-Type, and valid JSON payload. Keep minimum-configuration reads compact and synthesize curl only when requested. Deprecated commands such as `vesctl` remain filtered.

The shared `api-curl-guidance.md` fragment survives eager, progressive, custom, and transformed prompt composition. Scope native discovery and deletion instructions to default execution requests, and retain tests for both example-only behavior and explicit execution through the shell path.
